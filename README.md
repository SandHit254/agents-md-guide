# AGENTS.md 索引化规范

> 一套让 AI 编码助手的上下文文件**保持精炼、可维护、不腐烂**的工程规范。
> 适用于任何使用 `AGENTS.md` / `CLAUDE.md` / `.cursorrules` 等 agent 上下文文件的仓库。

## 它解决什么问题

AI 编码助手会**每次会话自动加载** `AGENTS.md`。于是几乎所有仓库都走向同一条路：

```
第 1 个月：AGENTS.md  3 KB    ← 清爽，是张"地图"
第 3 个月：AGENTS.md  40 KB   ← 开始膨胀，坑一条条往里堆
第 6 个月：AGENTS.md  125 KB  ← 每次会话烧掉 3 万 token 读它，且 84% 是陈年细节
```

**膨胀的代价是三重的**：

1. **成本** —— 每轮对话都重复加载，token 白烧
2. **失焦** —— 关键规则被淹没在历史细节里，agent 读不全等于没读
3. **腐烂** —— 没人愿意维护 125 KB 的文件，于是里面写的状态全是过期的

**本规范的核心主张**：

> **`AGENTS.md` 是「索引」，不是「百科全书」。
> 它只回答「去哪找」，不回答「是什么」。**

## 一、四层文档模型

| 层 | 是什么 | 体量红线 | 放什么 | 不放什么 |
|----|--------|---------|--------|---------|
| **全局 AGENTS.md** | 纲领 | **< 15 KB** | 跨项目通用规则：流程、原则、编码细则、沟通红线 | 任何具体项目的细节 |
| **项目 AGENTS.md** | 项目地图 | **< 30 KB** | 一句话结论 + **指向详细文档的路径** | 完整故障描述、逐条变更流水、长表格 |
| **详细文档** | 单一事实源 | 不限 | 完整过程、实证数据、可执行命令 | —— |
| **记忆 / memory** | 会话级自动加载 | —— | 环境/凭据/决策/进度 | 可从代码或文档查到的东西 |

**信息只能有一个权威位置**（单一事实源）。别处引用**只写路径，不复制内容**。

---

## 二、判定标准（一条信息该不该留在 AGENTS.md）

按顺序问三个问题：

| # | 问题 | 判断 |
|---|------|------|
| 1 | **它超过 2 行吗？** | 超过 → **下沉**，AGENTS.md 里只留一句话 + 指针 |
| 2 | **它只对某一次故障/某一个版本有意义吗？** | 是 → **下沉**到 `记录/经验/` 或台账 |
| 3 | **去掉它，agent 会做错事吗？** | 不会 → **删掉**，或下沉备查 |

**膨胀症状自查**（出现任一条即需重构）：

- 单行超过 **300 字**（一行塞完一整个故障的来龙去脉）
- 某个二级标题下超过 **8 KB**
- 全文超过体量红线
- **一次会话只用到其中一小节**，却要整份加载

## 三、下沉方法（三类高发内容）

三个章节会吃掉 80% 的体量，各有固定去处：

### 3.1 坑速查表 → `记录/经验/`

**反模式**（每个单元格塞完整描述）：

```markdown
| 坑 | 应对 |
|----|------|
| **多 key ConfigMap 单文件更新** | `create configmap --dry-run \| apply` 会把 ConfigMap 覆盖成单 key → 挂载缺失 CrashLoop（2026-09-08 login 事故）。必须 `kubectl patch --type merge --patch-file`；改前备份、改后验证 key 数量 |   ← 单行 300+ 字
```

**正确形态**（现象一句话 + 指针）：

```markdown
| 现象 | 详见 |
|------|------|
| 改 ConfigMap 后 pod CrashLoop，挂载文件缺失 | `记录/经验/多key-ConfigMap-单文件更新覆盖.md` |
```

**下沉目标文件的写法**：现象 → 根因 → 定位过程 → 修复命令 → 预防

### 3.2 模块状态表 → `记录/应用/<模块>/`

**反模式**：状态列里写满整个模块的历史、遗留问题、验证细节。

**正确形态**：状态 + 一句话，明细进该模块的落地文档。

```markdown
| 模块 | 状态 | 详见 |
|------|------|------|
| ITSM 品牌定制 | 已上线 | `记录/应用/itsm/品牌定制/` |
| CMDB 数据大屏 | 未开始 | —— |
```

### 3.3 变更记录 → `交付物/台账/`

**反模式**：AGENTS.md 里逐条记录每次改动（几行到几十行一条）。

**正确形态**：只留「日期 + 一句话 + 指针」，明细进分册台账。

```markdown
| 日期 | 变更 | 详见 |
|------|------|------|
| 2026-09-16 | 中转站 2.0.3：修编辑链路 bug + 视觉重构 | `交付物/台账/zt-bridge.md` §三 |
```

**台账分册原则**：一个交付物类型一份分册，单册超长时按「版本小节」切分，
并维护一个**索引文件**汇总各分册的当前状态。

## 四、暂存区治理（临时产物不污染项目）

**问题**：agent 会产生大量中间产物（一次性脚本、探测输出、日志、包副本、爬取素材）。
不加约束时，它们会平铺在一个目录里，几个月后变成 1000+ 文件没人敢清。

**规范**：临时产物一律落**项目外的单一暂存区**，且**分层**：

| 目录 | 放什么 | 可清理性 |
|------|--------|---------|
| `Temp/` | 真临时：跑完即弃的脚本、日志、缓存 | **随时可清** |
| `Tools/` | 可复用工具：跨会话/跨项目还会用 | 不要清（须登记） |
| `Ref/` | 参考资料：厂商文档、导出台账、上游源码参考 | 不要清 |
| `Archive/` | 归档：会话归档、旧版本产物、被取代的源码副本 | 谨慎 |
| `Docs/` | 文档产出：诊断报告、方案草稿 | 并入正式文档后可清 |
| `NotWork/` | 与工作无关的暂存 | 不管 |

**三条硬规矩**：

1. **暂存区根目录不放文件** —— 每个文件必须落在某一类里
2. **交付物只进项目仓库** —— 包 / 镜像 / 二进制归项目 `交付物/`，暂存区只允许临时副本
3. **反复要用的脚本必须升级** —— 从 `Temp/` 升到 `Tools/`，并在 `Tools/README.md` 登记

**分类判定流程**：

```
跑完这一次就没用了？        → Temp/
下次、别的项目还会用？      → Tools/
是别人给的资料/上游源码？   → Ref/
是旧版本/会话/被取代的？    → Archive/
是产出的文档？              → Docs/
跟工作无关？                → NotWork/
```

**暂存区必须有一份 `README.md`** 写清上表 + 清理规则 + 历史踩过的错。

## 五、初始化的检查清单

新建或接手一个仓库时，逐项核对：

- [ ] 全局 AGENTS.md < 15 KB，且**没有任何具体项目的细节**
- [ ] 项目 AGENTS.md < 30 KB，且**每条信息都能回答"去哪找"**
- [ ] 详细文档目录存在（`记录/` 或 `docs/`），且**每一条指针都能跳通**
- [ ] 有文档写作规范（见下方「四段式」）
- [ ] 暂存区已建立 6 类分层 + `README.md` 规约
- [ ] 项目 AGENTS.md 里**没有**超过 2 行的单元格
- [ ] 跑一次**断链检查**（所有指针路径都存在）

## 六、文档写作规范（详细文档用）

每份涉及改动的详细文档，用**四段式**：

| 段 | 回答的问题 |
|----|-----------|
| 一、为什么做 | 动机、背景、用户的原始诉求（引原话最好） |
| 二、改了什么 | 具体改动，含文件/命令/配置 |
| 三、结果如何 | 验证数据、实测取证，**不能只是"已完成"** |
| 四、后续维护评估 | **七维**（见下）—— 这是文档的核心增量 |

**维护评估七维**（缺一不可）：

| 维度 | 必须写清 |
|------|---------|
| 负债清单 | 新增/继承了哪些技术债，触发条件与影响面 |
| 升级适配 | 上游发新版时，本次改动如何重放、哪些行会冲突 |
| 失效风险 | 哪些依赖一旦变动会**静默失效** |
| 回滚成本 | 回滚命令、数据是否残留、需要多久 |
| 验证手段 | 下次改完跑什么命令能确认没弄坏 |
| 退役条件 | 什么情况下该重构或下线 |
| 维护频次与责任人 | 需要定期做什么，谁负责 |

> 只写"我做了什么"的文档没有价值 —— 那只是操作日志。
> **有价值的是"下次遇到同样的事，我怎么判断、怎么做、怎么验证"**。

## 七、常见反模式

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| **把 AGENTS.md 当日志写** | 每次改动追加一段 | 改动进台账，AGENTS.md 只更新指针 |
| **坑的描述写进表格单元格** | 单行 300+ 字 | 下沉到 `记录/经验/`，表格留现象 + 路径 |
| **状态表里写历史** | 「✅ 已完成，但当时因为 X 失败了三次最后用 Y 解决……」 | 留「✅ 已完成 + 指针」 |
| **复制而非引用** | 同一信息出现在 3 个文件里，改一处忘两处 | 单一事实源，别处只写路径 |
| **临时产物平铺** | 暂存区 1000+ 文件 | 按 6 类分层 |
| **交付物当临时文件存** | 暂存区堆着 1.5 G 的旧包 | 交付物只进项目仓库 |
| **指针指向不存在的文件** | 断链 | 每次改动后跑断链检查 |

## 八、一个真实案例（本规范的来源）

某项目 274 行的 `AGENTS.md` 长到了 **125 KB**，构成：

| 章节 | 体积 | 占比 |
|------|------|------|
| 坑速查表 | 38.5 KB | 31% |
| 模块状态表 | 34.6 KB | 28% |
| 变更记录 | 31.7 KB | 25% |
| 其余 8 节 | ~20 KB | 16% |

**84% 集中在三个"本该是指针"的章节**。同时它的暂存区平铺了 **1352 个文件 / 4.0 GB**：
865 个一次性脚本、1.5 G 与交付物重复的包副本、1.4 G 与工作无关的个人文件。

按本规范重构后：

- `AGENTS.md` 三个膨胀章节 → 各留一句话 + 指针
- 暂存区 4.0 G → 2.7 G（重复副本按 md5 验证后清理，释放 1.35 G）
- 顺手发现 **1.5 G 的"包历史"其实是服务器巡检快照**（内容与文件名完全不符）

**教训**：文件名会和内容撒谎 —— **判断一个归档是什么，先看内容再信名字**。
